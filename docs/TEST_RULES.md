# 命令テスト 記述規則

`emulator/src/tests/normal_tests.rs` を書くときの規則。

**前提**: `RESUME_GUIDE.md` 4.5.1 の「テスト設計の原則①〜⑧」が上位にある。
この文書はそれを命令テスト用に具体化したもので、原則と矛盾したらあちらが正。

規則の目的はひとつ ―― **書くたびに判断しないで済むようにすること。**
値や名前を毎回考えていると、そこに思考を取られて肝心の「何を検証するか」が疎かになる。

---

## 1. 書く前に答える5つの問い

**テストを1文字も書く前に、対象の `match` アーム（3〜5行）を読んで答える。**
実装が正解表になっているので、機械的に埋まる。

| 問い | `normal.rs` のどこを見るか |
|---|---|
| 1. メモリを**読む**か? 番地はどこから来るか? | `self.bus.read(??)` の `??` |
| 2. メモリに**書く**か? 番地はどこから来るか? | `self.bus.write(??, ..)` の `??` |
| 3. PC は動くか? 何バイト? | `fetch_byte()` の**呼び出し回数**（`fetch_word` は2回ぶん） |
| 4. どのレジスタが**変わる**か? | `self.registers.X = ` の**左辺**に出るもの |
| 5. サイクル数は? | アーム末尾の数字 |

演算命令ではこれに1問足す。

| 6. フラグ4つはそれぞれ「確定」か「保存」か? | `set_flags` なら4つとも確定、`update_flags` の `None` は保存 |

### 番地の調達元は4種類しかない

問い1・2の答えは必ずこのどれかになる。

| 調達元 | ニーモニックでの見え方 | 例 |
|---|---|---|
| **PC**（命令列の続き＝即値） | `n` / `nn` | `LD B, n`、`JP nn` |
| **レジスタペア** | `(HL)` `(BC)` `(DE)` | `LD (HL), A`、`LD A, (BC)` |
| **SP**（スタック） | ― | `PUSH` `POP` `CALL` `RET` |
| **命令に埋まった定数** | `0xFF00+`、RSTのベクタ | `LDH (n), A`、`RST 38H` |

**カッコ `( )` は「中身を番地として、そこのメモリ」を意味する。**
カッコが左（転送先）にあれば書き込み、右（転送元）にあれば読み出し。

**PC を特別扱いしないこと。** PC は「次の命令バイトの位置」という役割を持つだけの
16bitレジスタで、**即値を使う命令だけ**がそこを読む。
`LD A, (HL+)` にとって PC は無関係な箱でしかない。

## 2. 数値の割り当て（固定表）

**この表から選ぶ。その場で考えない。**

### 8bit の値

| 用途 | 値 | 備考 |
|---|---|---|
| 本命の値（読まれる / 書かれる） | **`0x5A`** | `0b0101_1010` |
| 対になる値（隣の番地、第2の対象） | **`0xA5`** | `0x5A` のビット反転 |
| 第3の値（上書き前の目印など） | **`0x3C`** | `0b0011_1100` |
| 第4の値 | **`0xC3`** | `0x3C` のビット反転 |
| レジスタ網羅の基準表 | **`0xB0 + index`** | B=`0xB0` C=`0xB1` … A=`0xB7`。下位ニブルが出所を表す |
| F レジスタ | **`0xF0`** | 下位4bitは実機で常に0 |
| 「あってはならない」印 | **`0xEE`** | |

**使ってはいけない値**（原則②）

- **`0x00`** ― 全メモリとレジスタの初期値。**Arrange を丸ごと忘れていても緑になる**
- **`0xFF`** ― 使用禁止領域の戻り値と衝突する
- **`0x10` `0x20` などキリのいい値** ― `assert_eq!` の出力は**10進**（`left: 16`）なので誤読しやすい

> 「LD 系は値を運ぶだけだからキリのいい値でよい」と考えたくなるが、
> **10進表示で読みにくい問題は命令の種類と無関係**に起きる。命令を問わず上の表から選ぶ。

### 16bit のアドレス

| 用途 | 値 |
|---|---|
| **PC**（命令列の位置） | **`0xC800`** 固定 |
| **データ用アドレス**（HL/BC/DE が指す先） | **`0xC100`** から、ブロックごとに **+`0x0100`**（`0xC100`〜`0xC700`） |
| **SP** | **`0xCF00`**（スタックは下に伸びるので上の方に置く） |
| 「あってはならない」印 | **`0xEEEE`** |

PC を `0xC8xx`、データを `0xC1xx`〜`0xC7xx` に分けているのは、
**失敗表示のアドレスを見た瞬間に「命令列の話かデータの話か」が分かる**ようにするため。

**避けるべきアドレス**

| アドレス | 理由 |
|---|---|
| `0x0000`〜`0x7FFF` | ROM 領域。`bus.write` が握り潰される（`bus.rs` の `write`） |
| `0xC000` | −1 で `0xBFFF`（ERAM）に出る |
| `0xDF00` 台 | +1 で `0xE000`（Echo RAM）に入り `0xC000` にミラーされる |
| `0xFE00` 以降 | OAM / 使用禁止領域 / IO。専用のテスト以外では使わない |

## 3. 変数の命名

### 大原則: **1つの変数を2つの役割に使わない**

これが実際に事故った。`LD (HL+), A` と `LD A, (HL+)` は A の役割が正反対
（**転送元** / **転送先**）なのに、両方 `value` という名前を使ったせいで、
ブロックをコピーしたときに向きを反転し忘れた。

**名前が役割を表していれば、コピペしても取り違えに気づける。**

| 役割 | 名前 |
|---|---|
| 実行**前**の値（不変を検証する、または上書き前の目印） | **`〜_before`** … `a_before` `f_before` `pc_before` `hl_before` |
| メモリの番地 | **`addr`** |
| その番地に置いた値 | **`mem`** |
| 隣の番地に置いた値 | **`mem_next`** / **`mem_prev`** |
| 即値オペランド | **`n`**（16bit は `nn`）― 仕様書の表記と揃う |
| ループ内の期待値 | **`expect`** |
| `execute()` の戻り値 | **`cycle`** |
| 網羅テストの基準表 | **`init`** |

**`value` `temp` `start` は使わない。** 役割を何も表さない。

### 名前が向きを教えてくれる例

```
0x22  LD (HL+), A   … A は転送元 → a_before を使う
                       assert: A が a_before のまま / read(addr) が a_before になった

0x2A  LD A, (HL+)   … A は転送先 → 期待値は mem
                       assert: A が mem になった（a_before は目印にしか使わない）
```

## 4. Arrange / Act / Assert の型

問い1〜5の答えが、そのまま3段構成に落ちる。

```
Arrange
  ・「読む場所」に値を置く            ← 問い1
  ・「書く場所」は初期値のままにする  ← 問い2（あとで汚れていないか見る）
  ・「変わるレジスタ」に目印を入れる  ← 問い4（上書きされたことを確認するため）
  ・「変わらないもの」に既知の値を入れる（PC, F は必ず）

Act
  let cycle = cpu.execute(opcode);

Assert
  下の「6. 並べる順序」のとおり
```

**「変わるレジスタ」に事前に目印を入れる**のを忘れやすい。
入れないと「正しく書き込まれた」と「そもそも書き込みが起きていない」を区別できない。

**PC と F は毎回必ず入れる。** どちらも初期値が `0x0000` / `0x00` なので、
そのままだと「0 に潰すバグ」を検出できない。
これは `new_cpu()`（11章）が代行するので、通常は意識しなくてよい。

## 5. assert の書き方

**① 引数順は `assert_eq!(実際, 期待, ...)` で固定**

`left` が常に実際の値、`right` が常に期待値になる。混在させると失敗表示を毎回読み解く羽目になる。

**② 第3引数は必ず書く**（原則⑤）

矢印の向きをデータの流れに合わせる。不変を主張するときは「不変」と書く。

```
"A -> (HL)"          … A の値がメモリへ書かれた
"(HL) -> A"          … メモリの値が A へ読まれた
"HL -> HL+1"         … HL が進んだ
"A + B -> A"         … 演算結果が転送先へ
"(HL+1) 不変"        … 更新後の番地は汚れていない
"F 不変"
"ZNHC -> 0010"       … F の期待値。4桁のビットで書く
```

**メッセージが名乗る範囲は、`assert_eq!` の第1引数が見ている範囲と一致させる。**

| 第1引数 | 検証しているもの | メッセージ |
|---|---|---|
| `cpu.registers.F` | Z N H C の**4つすべて** | `"ZNHC -> 0001"` |
| `cpu.registers.F & 0x80` | Z **だけ** | `"Z -> 0"` |

F 全体を比較している行に `"C -> 1"` と書くと、Z を消し忘れたバグで落ちたときに
**「C -> 1」と表示されるのに C は正しい**という食い違いが起きる。
1bit を名乗るのは、マスクして1bitだけ取り出している行に限る。

**メッセージは主張だけにする。理由・ビット列・計算は行末 `//` コメントへ。**

```
"A << 1"             // 0b1010_0101 -> 0b0100_1011 (Aのみで環状)
"ZNHC -> 0001"       // 入力問わずCに触れない(C=1)
```

括弧書きで `"A << 1 (Aのみで環状)"` のように足さない。
メッセージは**失敗表示に出る**ので短く読めることが要る。コメントは**読みに来たときだけ**要る。

### メッセージが区別するのは assert。命令はテスト名が区別する

**同じメッセージが複数のテストに現れてよい。** 失敗表示にはテスト関数名が必ず出るので、
どの命令の話かはそこで決まる。

```
---- tests::normal_tests::rra_shifts_carry_in_to_bit7 stdout ----   ← 命令はここで分かる
assertion `left == right` failed: A >> 1                            ← どの assert かはここ
  left: 181
 right: 173
```

メッセージに「他のテストと区別できる文言」を求め始めると、`"ZNHC -> 0000"` や `"F 不変"` の
ように**全テストで共有されている表現が全部説明不足になってしまう**。
メッセージの役目は**1本のテストの中で、落ちた assert を言い分けること**だけ。

逆に、1本の中に同じメッセージが2回出るときは接頭辞が要る（③の表）。

**③ opcode を入れるのは「どれが落ちたか」が分からないときだけ。入れるなら必ず変数から埋める**

| 状況 | `"0x{:02X}: "` の接頭辞 |
|---|---|
| 網羅ループ | **入れる。** さらに `index` も入れる |
| 1本のテストに複数 opcode のブロックを入れた | **入れる。** どのブロックかが分からなくなる |
| opcode が1つだけのテスト | **入れない。** `assert_pc_and_cycle` が opcode を出すので重複する |

```rust
assert_eq!(実際, 期待, "0x{:02X}: index {}", opcode, i);
```

接頭辞を機械的に全部に付けると、1行あたりの情報が増えるかわりに
**メッセージ本体（＝主張）が埋もれる**。テスト関数名と `assert_pc_and_cycle` で特定できる場合は付けない。

**リテラルを2箇所に書かないこと。**

```
let cycle = cpu.execute(0x2A);          ← ここと
assert_eq!(.., "0x2A: (HL) -> A");      ← ここが独立していると、片方だけ直せてしまう
```

この状態でブロックをコピーして `execute` 側だけ書き換えると、
**メッセージが嘘をついたままテストは緑になる**。実際にこれをやりかけた。

ブロックの先頭で `let opcode = 0x2A;` と束縛し、
`cpu.execute(opcode)` と書式引数の両方がそれを参照する。opcode が1箇所になれば、ずれようがない。

**④ 数値は16進で出す**

`assert_eq!` 本体は10進で表示するので、メッセージ側で `0x{:02X}` / `0x{:04X}` を使う。

## 6. assert を並べる順序（固定）

読む順が毎回同じになるので、書くときも漏れに気づきやすい。

```
1. 命令の主目的           … 転送先の値
2. 副作用                 … HL / SP の増減
3. 触っていないはずのもの … 隣のメモリ、他レジスタ、転送元
4. F
5. PC
6. cycle
```

3〜6 は「4.4 検証すべき5項目」でいう**忘れやすい下2つ**にあたる。機械的に並べて漏らさない。

## 7. 1つのテストに複数の opcode を入れるとき

分割の判断は原則④（同時に壊れるものだけまとめる）による。
`LD (HL+), A` と `LD A, (HL+)` のように**対になる命令**は1本でよい。

そのうえで:

- ブロックの先頭にコメントを置く ― `// === 0x22 (LD (HL+), A) ===`
- **`let mut cpu = Cpu::new(Bus::new());` で作り直す** ― 前ブロックの状態を持ち込まない
- `addr` を **`+0x0100`** する ― 失敗表示のアドレスでどのブロックか分かる
- assert メッセージに命令名を入れる

---

## 8. 網羅テスト（ループ）の型

`ld_r_r_all_opcodes` が参照実装。骨格は次のとおり。

```
init = [基準表]                  ← ループの外。一度だけ。最後まで変わらない
count = 0

for opcode in 範囲:
    opcode からパラメータを取り出す（ddd, sss など）
    対象外なら continue

    ── Arrange ──  内側ループで全レジスタを init に戻す（毎回必ず）
    ── Act ──      cycle = cpu.execute(opcode)
    ── Assert ──   内側ループで全レジスタを検証
                   期待値 = if 転送先 { init[転送元] } else { init[自分] }
                   F, PC, cycle も
    count += 1

ループの後: count == 期待件数
```

**必ず守ること**

- **Arrange の内側ループを毎回まわす。** 前の反復の結果が残ると期待値が崩れる
- **`ddd` 以外のレジスタも全部検証する。** 転送先の取り違えはこれでしか捕まらない
- **最後に `count` を検証する。** `continue` の条件を間違えて**全件スキップしても緑になる**
- 配列の添字は `usize`。`init[ddd as usize]` の変換が要る

## 9. よくある失敗（実際にやったもの）

| 症状 | 原因 |
|---|---|
| `left: 0` が出る | Arrange で値を置き忘れ / ROM 領域に置いて write が無視された / 読む番地がずれている |
| オペランドが読まれない | `execute()` はオペコードを fetch しない。**呼ぶ直前の PC はオペランドの先頭を指す** |
| PC と HL が混ざる | 番地の調達元は命令ごとに違う。1章の表で確認する |
| コピーしたブロックが逆向き | `value` のような役割不明の名前を使った。3章の命名に従う |
| `get_hl()` で読んで満足する | アドレスは**決めて `set_hl()` で入れる**。`get_hl()` は初期値 `0x0000` を返すだけ |
| 空のテストが緑のまま | 中身のない `fn` は必ず通る（原則⑦）。**一度赤を見る**まで完了ではない |

## 10. 完成の条件

原則⑦・⑧より、**緑になっただけでは終わっていない。**

1. 期待値をわざと1つずらして**赤を見る**
2. 節目では**実装をわざと壊して**（ミューテーション）、狙った assert が落ちるか確認する
   - 例: `LD (HL+), A` の `write` と `set_hl` を入れ替えると、
     **「HL が +1 された」は通ったまま**「更新前の番地に書かれた」だけが落ちる
3. 確認したら**必ず元に戻す**。実験の前は必ずコミット済みの状態にしておくこと

## 11. ヘルパーと共通化の線引き

テストが増えると「これ毎回書いているな」という部分が出てくる。
共通化してよいものと、してはいけないものがある。**基準はひとつ。**

> **その値・その行に「正解」があるか?**
>
> - **正解がない**（任意の既知の値でよい / 全テストで必ず同じ）→ **共通化してよい**
> - **正解がある**（何を検証するかを表している）→ **共通化してはいけない**

後者を隠すと、`RESUME_GUIDE.md` 原則④(隠れる失敗の量)・⑤(メッセージが矛盾を暴く)・
4.4(忘れやすい下2つ)が同時に効かなくなる。

### 11.1 定数化してよい値 / いけない値

| 値 | 正解があるか | 定数化 |
|---|---|---|
| `PC_BEFORE` = `0xC800` | ✅ 規則で固定（データ用アドレスと区別する） | **する** |
| `F_BEFORE` = `0xF0` | ✅ 仕様（下位4bitは常に0） | **する** |
| `POISON` = `0xEE` | ✅ 「あってはならない」という**意味**を持つ | **する** |
| `REG_INIT` = `[0xB0+i]` | ✅ 「下位ニブルが出所を表す」という規則 | **する** |
| `0x5A` `0xA5` `0x3C` `0xC3` | ❌ **単に互いに違う任意の値**。`0x69` でも成立する | **しない** |

`0x5A` を `const MAIN` のようにすると「MAIN には特別な意味がある」と誤って示唆する。
実際には区別可能な適当な値でしかない。
**役割の説明は `a_before` / `mem` / `mem_next` というローカル変数名が既に担っている。**

### 11.2 番人とポイズンは別物

| | 意味 | 値 | assert の形 |
|---|---|---|---|
| **番人** | 「**変わらないはず**の普通の値」 | `0xA5` など | `assert_eq!(read(addr+1), mem_next)` |
| **ポイズン** | 「**読まれても書かれてもいけない**」 | `POISON` | 等値比較の期待値に出てこない。出現したら異常 |

`LD (HL+), A` で `addr+1` に置くのは**番人**。
`reg_get(6)` のような「到達したら設計が壊れている」場所が**ポイズン**の出番。

### 11.3 関数化してよいもの / いけないもの

| 対象 | 判断 | 理由 |
|---|---|---|
| `new_cpu()`（CPU生成 + PC + F） | ✅ **する** | 全テストで必ず同じ。入れ忘れが構造的に起きなくなる |
| `reg_get` / `reg_set`（index→レジスタ） | ✅ **する** | 網羅ループに必須。分岐表であって検証ではない |
| **assert のメッセージ本文** | ❌ **しない** | 定型文ではなく**主張**。手で書くから矛盾に気づける（原則⑤） |
| **F / PC / cycle をまとめる `assert_common`** | ❌ **しない** | 4.4 の「忘れやすい下2つ」を隠すことになる |
| 引数を多く取るセットアップ関数 | ❌ **しない** | 呼び出し側が位置引数の羅列になり、Arrange が読めなくなる |

**ヘルパーは引数ゼロか1つに留める。**

> 技術メモ: 「関数にすると失敗行がヘルパーを指す」問題は、`macro_rules!`(呼び出し位置に展開される)
> または `#[track_caller]` を付けた関数で回避できる。
> つまり上の ❌ は**行番号の問題ではなく、読み手が別の場所を見に行く必要が出る**ことが理由。

### 11.4 現在のヘルパー（`normal_tests.rs`）

```
const PC_BEFORE / F_BEFORE / POISON / REG_INIT
fn   new_cpu() -> Cpu          … Cpu::new(Bus::new()) + PC + F
fn   reg_get(cpu, i) -> u8     … index → レジスタ（getter）
fn   reg_set(cpu, i, v)        … index → レジスタ（setter）
```

`reg_get` / `reg_set` を2本に分けているのは借用のため。
`fn reg_mut(&mut Cpu, i) -> &mut u8` の1本にまとめると、
返された `&mut` が生きている間 `cpu` を可変借用し続けるので、
同じ式の中で別のレジスタを読めなくなる。

`bus_tests.rs` など他ファイルからも使いたくなったら、そのとき共通モジュールへ移す。
**先回りしない。**
