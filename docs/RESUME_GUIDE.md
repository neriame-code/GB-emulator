## 1. 基礎の復習

### 1.1 命令実行サイクル ― PCは誰のものか

CPUの動作はこの繰り返しだけ。

```
┌─ FETCH ──→ PCの指すバイトを読む。PC += 1
│
├─ DECODE ─→ そのバイトが何の命令か判定する
│
├─ EXECUTE → 命令を実行する。オペランドが要るなら「さらに」読む（PCが進む）
│
└─ 実行にかかったサイクル数を返す ─→ 先頭に戻る
```

この責務は2箇所に分かれている:

| 担当 | 誰がやるか | 現状 |
|---|---|---|
| FETCH（オペコード1バイト） | **呼び出し側**（未実装の `step()`） | ❌ |
| DECODE | `execute()` の `match opcode` | ✅ |
| EXECUTE + オペランド読み | `match` の各アーム | ✅ |
| サイクル数を返す | 各アームの末尾の数値 | ✅ |

**最重要**: `execute(&mut self, opcode: u8)` は opcode を**引数で受け取っている**。
つまり**1バイト目はすでに消費済み**。各アームが `fetch_byte()` すべき回数は:

```
アーム内の fetch 回数 = 命令の全長 − 1
```

| 命令 | 全長 | アーム内 fetch |
|---|---|---|
| `NOP` (0x00) | 1 | 0回 |
| `LD B, n` (0x06) | 2 | 1回 |
| `STOP` (0x10) | 2 | **1回**（修正前は2回でバグ） |
| `LD BC, nn` (0x01) | 3 | 2回（= `fetch_word()`） |

`0xCB` のアームがこの前提を体現している。CB命令は全長2バイトだが `fetch_byte()` は1回だけ:

```rust
0xCB => {
    let opecode = self.fetch_byte();  // 2バイト目だけを読む
    self.prefix_execute(opecode)
},
```

#### STOP のバグが何を引き起こすか

`0xC000` に `10 00 3E 42`（`STOP` / `LD A,0x42`）が置かれている場合:

```
呼び出し側:  opcode = fetch_byte() → 0x10 を読む、PC: C000 → C001
execute(0x10) 内:
  正しい:  fetch_byte() ×1 → PC: C001 → C002   ✅ 次は 3E (LD A,n)
  修正前:  fetch_byte() ×2 → PC: C001 → C003   ❌ 次は 42 (ただのデータ)
```

`LD A, 0x42` のオペコードを食い潰し、データ `0x42`（= `LD B,D`）を命令として実行し始める。
以降は完全に別のコードが走る。

### 1.2 「命令長」と「サイクル数」は別物

- **命令長（バイト数）** … PCがいくつ進むか。ROMを何バイト消費するか
- **サイクル数（T-cycle）** … 実行に何クロックかかるか。**PPUとTimerを進めるための時間の単位**

この2つは比例しない。

```rust
0xE9 => { self.registers.PC = self.registers.get_hl(); 4 },  // JP (HL):    1バイト /  4サイクル
0x08 => { /* LD (nn), SP */                              20 },  // LD (nn),SP: 3バイト / 20サイクル
```

サイクル数を返すのは、後で `emulator.rs` がこう書けるようにするため:

```
cycles = cpu.step();
ppu.tick(cycles);     // PPUを同じ時間だけ進める
timer.tick(cycles);   // Timerも同じ時間だけ進める
```

**これがエミュレータの心臓部**。CPUが「4サイクル使った」と申告し、その分だけ他のデバイスを進める。
この同期があるからゲームの速度が正しくなる。

条件分岐命令が `16 / 12` のように2つの値を返しうるのは、
**分岐が成立するとPCの書き換えに追加のサイクルがかかる**ため。

### 1.3 `set_flags` と `update_flags` の使い分け

Fレジスタは上位4bitのみ使用（`Z N H C`、下位4bitは常に0）。命令ごとに触るフラグが違う。

```
ADD A, B  →  Z * / N 0 / H * / C *    4つ全部確定    → set_flags でよい
INC B     →  Z * / N 0 / H * / C -    Cだけ変化なし  → update_flags が必要
```

`INC B` が C を変えないのは、16bit加算を8bit命令で組み立てるときに
キャリーを保持したまま `INC` を挟めるようにするため。

```rust
0x04 => { // INC B
    self.registers.update_flags(Some(result==0), Some(false), Some(h), None);
    //                                                                  ↑ C は None = 保持
```

> **仕様書のフラグ欄 `-` が `None` に対応する。**

### 1.4 ハーフキャリー（H）とは何か

**H = bit3 から bit4 への繰り上がりが起きたか**（下位ニブルからの繰り上がり）。

```
  0b0000_1111  (0x0F)
+ 0b0000_0001  (0x01)
  ───────────
  0b0001_0000  (0x10)
       ↑ ここに繰り上がった → H = 1
```

判定式のパターン:

```rust
// 加算: 下位4bit同士を足して 0xF を超えたか
let h = (self.registers.A & 0xF) + (r & 0xF) > 0xF;

// 減算: 下位4bitが借りを必要とするか
let h = (self.registers.A & 0xF) < (r & 0xF);

// INC: 下位4bitが 0xF なら +1 で必ず繰り上がる
let h = self.registers.B & 0xF == 0xF;

// DEC: 下位4bitが 0x0 なら -1 で必ず借りる
let h = self.registers.B & 0xF == 0x0;

// 16bit演算は基準が bit11 → bit12（0xFFF であって 0xF ではない）
let h = (self.registers.get_hl() & 0xFFF) + (r & 0xFFF) > 0xFFF;
```

**Hは何のためにあるか**: ほぼ `DAA` 専用。BCD（10進数を4bitずつに詰める表現）で
スコア計算をするゲームのために存在する。
逆に言えば DAA を使わない限り表面化しないので、**バグに気づきにくいフラグ**。

> **Rustの豆知識**: `A & 0x0F > 0x09` は Rust では `(A & 0x0F) > 0x09` と解釈される。
> Rustの優先順位は `&` のほうが比較演算子より**高い**（C言語とは逆）。そのまま書いてよい。

## 2. メモリマップ

CPUは16bitアドレス＝**0x0000〜0xFFFF の64KB空間**しか見えない。
ここに ROM も RAM も I/O も全部並ぶ（メモリマップドI/O）。

| 範囲 | 用途 | サイズ | フィールド |
|---|---|---|---|
| `0x0000`–`0x3FFF` | ROM Bank 0（固定） | 16KB | `rom` |
| `0x4000`–`0x7FFF` | ROM Bank 1〜N（MBCで切替） | 16KB | `rom` |
| `0x8000`–`0x9FFF` | VRAM（タイル・BGマップ） | 8KB | `vram` |
| `0xA000`–`0xBFFF` | External RAM（カートリッジ上のセーブ用） | 8KB | `eram` |
| `0xC000`–`0xDFFF` | WRAM（本体内蔵RAM） | 8KB | `wram` |
| `0xE000`–`0xFDFF` | **Echo RAM**（`0xC000`〜`0xDDFF` のミラー） | — | `wram` |
| `0xFE00`–`0xFE9F` | OAM（スプライト属性40個分） | 160B = `0xA0` | `oam` |
| `0xFEA0`–`0xFEFF` | 使用禁止領域 | — | — |
| `0xFF00`–`0xFF7F` | **I/Oレジスタ** | 128B = `0x80` | `io` |
| `0xFF80`–`0xFFFE` | HRAM（高速な作業領域） | 127B = `0x7F` | `hram` |
| `0xFFFF` | IE（割り込み有効フラグ） | 1B | `ie` |

### 押さえるべき3点

**① Echo RAM** — `0xE000`〜`0xFDFF` は `0xC000`〜`0xDDFF` と**物理的に同じメモリ**。
ハード設計上たまたまそうなった領域だが、実際にアクセスするゲームが存在する。
`addr - 0x2000` に読み替えるだけ。

**② HRAM が別にある理由** — `LDH` 命令（`0xE0`/`0xF0`、実装済み）は `0xFF00 + n` を
1バイトのオペランドで指せる。命令が短く速いので頻繁に使う変数をここに置く。
**スタックもここに置かれることが多い**。

**③ I/O レジスタこそが「デバイスとの通信路」** — `0xFF40` に書けばLCDの設定が変わり、
`0xFF44` を読めば現在のスキャンラインがわかる。
**PPU・Timer・Joypadは全部この窓口経由でCPUと繋がる。**
いまは `[u8; 0x80]` の素の配列でよいが、後でここが
`self.ppu.read_register(addr)` のような転送に変わる。
**今の設計で最も将来変わる場所**だと意識しておく。

## 3. 【完了】`bus.rs` の実装

### 3.1 使う道具

#### 範囲パターンマッチ

```rust
pub fn read(&self, addr: u16) -> u8 {
    match addr {
        0x0000..=0x7FFF => { /* rom から読む */ }
        0x8000..=0x9FFF => { /* vram から読む */ }
        // ...
    }
}
```

`..=` は**両端を含む**範囲（`..` は上限を含まないので、アドレス指定では必ず `..=`）。
`match` は網羅性がコンパイル時にチェックされるため、`0x0000`〜`0xFFFF` を
カバーしないとコンパイルエラーになる。**これは味方** — 領域の書き漏らしを防いでくれる。

#### インデックス変換

配列は0始まりだがアドレスはそうではない。**必ずベースアドレスを引く**。

```
VRAM は 0x8000 から始まり、vram 配列は 0 から始まる
  → vram[addr - 0x8000]

addr = 0x8000 → index 0
addr = 0x9FFF → index 0x1FFF (= 8191, 配列の最後)  ✅
```

Rustでは**配列の添字は `usize`** でなければならない:

```rust
self.vram[(addr - 0x8000) as usize]
```

> `as usize` の位置に注意。`(addr as usize) - 0x8000` でも結果は同じだが、
> `addr - 0x8000` を先に行うと `addr < 0x8000` のとき **u16のアンダーフローでpanic** する。
> `match` で範囲を絞った後なら起きないが、意識しておくと安全。

### 3.2 ハマりどころ

#### ① `#[derive(Default)]` が使えない

```rust
#[derive(Default)]
struct Bus { vram: [u8; 0x2000] }   // ❌ コンパイルエラー
```
```
error[E0277]: the trait bound `[u8; 8192]: Default` is not satisfied
```

標準ライブラリの `Default` は**要素数32までの配列にしか実装されていない**。手で書く:

```rust
impl Bus {
    pub fn new() -> Self {
        Bus {
            rom:  vec![0; 0x8000],
            vram: [0; 0x2000],
            // ...
        }
    }
}
```

`[0; 0x2000]` は「0を8192個並べた配列」を作るリテラル構文（`vec![0; n]` はそのVec版）。

#### ② `rom` は `Vec` なので長さが保証されない

`rom: Vec<u8>` は実行時に長さが決まる。ROMを読み込んでいないテストで
`rom[0x1234]` を読むと **index out of bounds でpanic** する。対処は2つ:

- **A案**: `Bus::new()` で必ず `vec![0; 0x8000]` を確保する（単純。今はこれで十分）
- **B案**: `self.rom.get(i).copied().unwrap_or(0xFF)` で範囲外を安全に処理する
  （`get` は `Option<&u8>` を返す。実機の未接続アドレスは `0xFF` を返すのでこちらがより正確）

#### ③ 書き込んではいけない領域

- `0x0000`–`0x7FFF` … ROM（読み取り専用）。**無視するだけにする**。
  `panic!` にしてはいけない — 後でここへの書き込みが **MBCのバンク切替コマンド**になる
- `0xFEA0`–`0xFEFF` … 使用禁止領域。無視
- 読み出し時の使用禁止領域は `0xFF` を返すのが慣例

| アドレス | 何が特殊か | いつ必要になるか |

## 4. テストの準備と作成

### 4.1 コンストラクタを用意する

いま `Cpu` にコンストラクタがない。テストごとに全フィールドを手で埋めるのは苦痛なので入口を作る。

```rust
impl Registers {
    pub fn new() -> Self { /* 全部0で初期化 */ }
}

impl Cpu {
    pub fn new(bus: Bus) -> Self { /* registers, bus, ime:false, halted:false, ei_pending:false */ }
}
```

> **`pub(crate)` について**: `Registers` のフィールドは `pub(crate)`＝「このクレート内からのみ見える」。
> ユニットテストを `src/` の中に書く限り同じクレートなので `cpu.registers.A` に直接アクセスできる。
> **今の可視性のままでよい。**
> （`tests/` ディレクトリの統合テストは別クレート扱いになりアクセスできない。
> CPU内部の検証は `src/` 内のユニットテストが適切）

### 4.2 Rustのテストの書き方

テスト対象と同じファイルの末尾に書くのがRustの流儀。

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn nop_advances_pc_and_costs_4_cycles() {
        // ここに処理
    }
}
```

| 記述 | 意味 |
|---|---|
| `#[cfg(test)]` | **条件付きコンパイル**。`cargo test` のときだけビルドする。`cargo build` では存在ごと消えるので製品バイナリに影響しない |
| `mod tests` | 単なるモジュール。名前は慣例で `tests` |
| `use super::*;` | **親モジュールの中身を全部取り込む**。これがないと `Cpu` も `Flag` も名前解決できない |
| `#[test]` | この関数をテストとして登録する。引数なし・戻り値なしが基本形 |

#### アサーションマクロ

```rust
assert_eq!(実際の値, 期待値);
assert_eq!(cpu.registers.A, 0x42, "A の値が違う");  // 第3引数以降はエラー時のメッセージ
assert!(条件);
assert!(!cpu.registers.get_flag(Flag::Z), "Z が立ってはいけない");
```

失敗すると `panic!` してそのテストだけが赤くなる。他のテストは続行される。

### 4.3 テストの型（Arrange-Act-Assert）

CPU命令のテストは**必ず同じ3段構成**になる。この型を体に入れる。

```
1. Arrange … CPUを既知の状態にする
              （レジスタに値を入れる、メモリに命令バイトを置く、PCをそこに向ける）
2. Act     … 命令を1つ実行する
              （cycles = cpu.execute(opcode)）
3. Assert  … 結果を検証する
              （レジスタ / フラグ / メモリ / PC / サイクル数）
```

### 4.4 検証すべき5項目

命令1つにつき次を確認する癖をつける。**特に下2つを忘れがち**:

1. 結果の値（レジスタ or メモリ）
2. フラグ4つ ― **変化しないはずのフラグが保たれているかも含む**（`update_flags` の `None` の検証）
3. **PC** が正しいバイト数だけ進んだか ← STOPのバグはこれで検出できる
4. **返り値のサイクル数**
5. SP（スタック操作命令の場合）

### 4.5 【完了】Bus のテスト（命令テストより先）

#### 4.5.1 テスト設計の原則（Busテストで得た指針）

**命令テストでもそのまま使えるので、書き始める前にここを読み返すこと。**

**① 往復テストだけでは対称バグを検出できない**

`read` と `write` が**同じズレ方**をしていると、往復させても打ち消し合って緑になる。

```
write(0x9FFF, v) → read(0x9FFF) == v   … 両方が -0x8001 でも通ってしまう
write(0x9FFF, v) → bus.vram[0x1FFF]    … フィールドを直接見れば暴ける
```

実際にこれを実測した。Echo RAM の範囲を1バイト伸ばす故障を入れたとき、
`oam_roundtrip` は**通り**、`boundary_oam`（フィールド直接）だけが落ちた。

→ **片方だけを通し、もう片方は素の状態を見る。** 往復は疎通確認と割り切る。

**② テストに使う値は「偶然その値になる確率が低いもの」を選ぶ**

- `0x00` は禁止。全メモリの初期値なので、**書き込みが丸ごと無視されていても緑になる**
- `0xFF` も避ける。使用禁止領域の戻り値と衝突する
- `0x10` `0x20` も避けたい。`assert_eq!` の出力は**10進**（`left: 16`）なので誤読しやすい
- `0xA5`（`0b1010_0101`）`0x5A` が最適。ビットが交互で、マスク・シフトのミスも暴ける

**③ 1つのテストで複数の対象を触るときは、対象ごとに違う値を使う**

境界値テストで7領域すべてに `0x01` を書くと、「隣の領域に漏れている」バグを見逃す。
実際に `bus.eram` と `bus.wram` の書き間違いを、違う値にしていたおかげで検出できた。

**④ 分割の判断基準は「隠れる失敗の量」**

`assert_eq!` は失敗すると `panic!` してその関数を即座に終わらせる。
1本にまとめると、**最初の失敗より後ろは実行されない**。

```
まとめる → 修正・実行を4往復して、ようやく4箇所のミスが出そろう
分ける   → 1回の実行で4本同時に赤くなる
```

> **同時に壊れるものだけをまとめる。独立に壊れうるものは分ける。**

`bus.rs` の `match` は領域ごとに独立したアームなので、7つの独立した関心だった。
逆に、`write` の式と `read` の式（各2行）は同じテスト内でよい — 隠れる量が1アサート分しかないため。

**⑤ `assert_eq!` の第3引数は必ず書く**

`left: 3 / right: 5` という数字だけでは、何と何を比べたのか分からず必ずソースを開くことになる。
**検証している対応関係**を書くと、出力だけで判断できる。

```
write 側:  "write(0x9FFF) -> vram[0x1FFF]"
read  側:  "vram[0x1FFF] -> read(0x9FFF)"
```

矢印の向きをデータの流れに合わせると、テストの意図がそのまま文になる。
実際、`read` に配列の添字を渡してしまったミスは、`"vram.read(0x0000)"` という
**メッセージ自体の矛盾**で気づけた。

**⑥ テストが落ちたら、疑う順番は「テスト自身 → 実装」**

新しく書いたばかりのテストのほうが、何度も動かしてきた実装よりバグを含む確率が高い。
ここを逆にすると、正しい実装をいじって壊す事故が起きる。

**⑦ 緑は「正しい」ではなく「panic しなかった」**

中身が空の `fn foo() {}` は緑になる。期待値をわざと1つずらして
**一度赤を見る**ところまでが、テストを書く作業に含まれる。

**⑧ 検出力を測るならミューテーションテスト**

**実装をわざと壊して、テストが赤くなるか**を見る。カバレッジ率（何行実行されたか）は
「実行したけど何も検証していない」を区別できないが、この方法は誤魔化しが効かない。
節目ごとに手作業で数パターン試すだけでも、穴の位置が分かる。

```
1つの故障につき、落ちるのは1〜2本  ← 理想
1つの故障で5本落ちる               ← まとめすぎ。原因の特定が遅くなる
どの故障でも落ちない               ← そこがテストの穴
```

### 6.1 CB命令（`cb.rs`）

**256個を手書きしないこと**が学習ポイント。CB命令のビットパターンには強い規則性がある。

```
opcode = 0b_XXXXX_TTT
              ↑     ↑
              演算  ターゲット(3bit)
```

- 下位3bit `TTT` → `0..7` = `B, C, D, E, H, L, (HL), A`
  （`normal.rs` の `0x40`〜`0x7F` の LD と全く同じ並び）
- `0x00`–`0x3F` → 上位5bitで `RLC/RRC/RL/RR/SLA/SRA/SWAP/SRL` の8種
- `0x40`–`0x7F` → `BIT n, r`（`n = (opcode >> 3) & 7`）
- `0x80`–`0xBF` → `RES n, r`
- `0xC0`–`0xFF` → `SET n, r`

設計の勘所:

1. `fn read_target(&mut self, t: u8) -> u8` / `fn write_target(&mut self, t: u8, v: u8)` を先に作る
2. サイクル数は `if t == 6 { 16 } else { 8 }` で一律に出る
   （**例外: `BIT n, (HL)` だけ書き戻しが無いので 12**）
3. 演算本体は `fn rlc(&mut self, v: u8) -> u8` のように、フラグ更新込みの純粋な関数群にする

`0x00..=0x3F` は `match opcode >> 3` で8分岐、あとは3つのレンジで済む。実質50行程度。

> **罠**: `RLC A`（CB 0x07）と normal の `RLCA`（0x07）はフラグが違う。
> **RLCAはZを常に0**にするが、**CB版のRLC Aは結果に応じてZを立てる**。

### 6.2 残りの命令テスト ― 分担して作成（手順4の後）

`normal_tests.rs` には `#[ignore]` のまま残る雛形が多数ある。
全部を手で書くのは、学習効果に対して時間がかかりすぎる。
**テストの学習価値は本数に比例しない**ので、種類で線を引いて分担する。

| 種別 | 扱い | 理由 |
|---|---|---|
| **網羅ループ系**<br>`*_all_registers` `*_all_pairs` `*_all_sources` など | Claude に書かせる | `ld_r_r_all_opcodes` という参照実装が既にある。型が確立済みで学びの残量が少ない |
| **単純確認系**<br>`and/or/xor/cp` の result・flag、`inc/dec` の派生 | Claude に書かせる | 既に書いた `add/sub` 系の変形でしかない |
| **境界値・仕様系** | **自分で書く** | 期待値を決める工程そのものが目的 |

自分で書くものの内訳（符号拡張・半キャリー・BCD補正・バイト順）:

```
ld_hl_sp_e_flags_from_low_byte      ld_hl_sp_e_negative_offset
add_sp_e_flags_from_low_byte        add_sp_e_negative_offset
sbc_a_b_half_borrow_includes_carry_in
daa_after_subtraction               daa_sets_carry_on_upper_adjust
ld_nn_sp_writes_low_byte_first      jr_e_is_relative_to_next_instruction
push_bc_stores_high_byte_at_higher_address
```

「`LD HL, SP+e` のH/Cは下位バイト由来」「`ADD SP, e` の `e` は符号付きなのに
フラグは符号なし8bit加算として立つ」あたりは、**自分で期待値を決めないと頭に入らない**。

#### 守ること

**緑になっただけでは終わっていない。** 他人が書いたテストが一発で通った場合、
得られる情報はゼロ ―― 検出力があるのか、実装と同じ勘違いを共有しているだけなのかが
区別できない（10章と同じ話）。したがって:

1. **ミューテーションテストは必ず自分でやる。** 実装をわざと1箇所壊し、
   狙った assert が落ちるか確認する。ここが「読んだ」を「理解した」に変える唯一の工程
2. **群単位（10〜15本）で回す。** 一気に生成するとレビューが追いつかず「読んだつもり」になる
3. assert を読む前に**自分で期待値を言ってから答え合わせ**する。
   コメントを書くのは強制力が弱い（理解していなくても書ける）。ズレた箇所だけが学ぶべき場所

### 6.3 `Cpu::step()` と割り込み

```
step():
  1. 割り込みチェック（IME && (IE & IF & 0x1F) != 0 なら割り込みサービス）
     └ IME=false → 対応するIFビットをクリア → PCをpush → PC=ベクタ → 20サイクル
  2. ei_pending の消化（EIの1命令遅延）
  3. halted なら 4サイクル返して終了（ただし IE&IF != 0 なら halt解除）
  4. fetch_byte() → execute()
```

`ei_pending` を「いつ `ime = true` にするか」が難しい。
**EI命令の次の命令が実行された後**にIMEが立つ、という順序を守る。

## 付録A: この作業で踏んだRustの落とし穴

同じところで再度詰まらないための記録。

### A.1 構造体の「定義」と「初期化」は見た目が同じで意味が違う

```rust
// 定義（struct Bus { ... }）  → 右側は【型】
pub ie: u8,

// 初期化（Bus { ... }）       → 右側は【値】
ie: 0,
```

`ie: u8,` を初期化側に書くと `expected value, found builtin type` になる。

### A.2 `#[derive(Default)]` は要素数32超の配列に使えない

```
error[E0277]: the trait bound `[u8; 8192]: Default` is not satisfied
```

標準ライブラリの `Default` 実装が配列に対して**要素数32まで**しか無いため。
`Bus::new()` のように手で書く。`[0; 0x2000]` が「0を8192個並べた配列」のリテラル。

### A.3 `match` は文ではなく【式】

`match` 自体が値を持つ。`if` も同じ。

```rust
pub fn read(&self, addr: u16) -> u8 {
    match addr {
        0x0000..=0x7FFF => self.rom[addr as usize],   // セミコロンなし = アームの値
        // ...
    }   // ← match の値がそのまま関数の戻り値（末尾なのでセミコロン不要）
}
```

| 記法 | 意味 |
|---|---|
| `=> 式,` | 短い場合はブロックなしで直接書く。カンマで区切る |
| `=> { ...; 式 }` | ブロックの場合、**最後の式にセミコロンを付けない**とそれがブロックの値 |
| `=> { 式; }` | セミコロンを付けると値が捨てられて `()` になる |

`normal.rs` の各アームが末尾にセミコロン無しでサイクル数を書いているのと同じ仕組み。

### A.4 `todo!()` はパターンの位置に置けない

```rust
match opcode {
    todo!("...")        // ❌ error: non-pattern macro in pattern position
}
```

`match` の中身は `パターン => 式` の形でなければならない。
`match` ごと消すか、`_ => todo!("...")` と書く（`_` = 何にでもマッチするパターン）。

### A.5 モジュールパスと型の関連関数は別物

```rust
registers::new()    // ❌ registers【モジュール】直下の自由関数を探す
Registers::new()    // ✅ Registers【型】の関連関数を呼ぶ
```

`pub mod registers;` の `registers` と `struct Registers` は名前が似ているだけの別物。

### A.6 フィールド初期化の短縮記法

フィールド名と変数名が同じときは片方を省ける。

```rust
Cpu { registers: Registers::new(), bus: bus, ... }   // 冗長
Cpu { registers: Registers::new(), bus, ... }        // 短縮記法
```

### A.7 `as usize` を書く位置

```rust
self.vram[(addr - 0x8000) as usize]   // 推奨
(addr as usize) - 0x8000              // 結果は同じだが…
```

前者は `addr < 0x8000` のとき **u16のアンダーフローでpanic** する。
`match` で範囲を絞った後なら起きないが、意識しておくと安全。

### A.8 アドレス変換は「アドレス空間の値」と「配列の添字」を混同しない

Echo RAM のバグの原因。

```
ステップ1: Echo → WRAM のアドレスに変換     addr - 0x2000   （0xE000 → 0xC000）
ステップ2: WRAM のアドレス → 配列の添字      さらに - 0xC000 （0xC000 → 0）
```

`- 0x2000` だけで止めると `wram[49152]` を引いて index out of bounds になる。

> **この取り違えはテスト側でも再発した。** `bus.vram[0x1FFF]` に値を置いたあと、
> `bus.read(0x1FFF)` と書いてしまった（`0x1FFF` は ROM 領域のアドレス）。
> 正しくは `bus.read(0x9FFF)`。**`read`/`write` が受け取るのはアドレス空間の値**であって、
> 配列の添字ではない。この2つの世界を行き来する場所では、実装でもテストでも繰り返し出る。

### A.9 `u16` の `..=` ループはオーバーフローしない

C言語の `for (uint16_t i = 0; i <= 0xFFFF; i++)` は無限ループになるが、**Rustでは起きない**。

```rust
for addr in 0x0000u16..=0xFFFF { ... }   // 65536回きちんと回る
```

`RangeInclusive` は「終端に達したか」を内部フラグで持っていて、`u16::MAX` の次を計算しない。
`u32` で回して `as u16` する必要はない。

（`0..0xFFFF` と `..` で書くと `0xFFFF` が**含まれない**ので、アドレス空間では必ず `..=` を使う。3.1と同じ話）

## 付録B: `panic!` を使ってよい場所・悪い場所

エミュレータでは特に重要な判断基準。

| 状況 | 対応 |
|---|---|
| **エミュレータ自身のバグ**（自分のコードの想定外） | `panic!` / `unreachable!` でよい。早く気づきたい |
| **未実装**（これから書く） | `todo!()` が適切。メッセージに何が来たか出す |
| **ゲーム側の行儀の悪い動作**（実機なら動く） | **panic 禁止**。実機の挙動を真似る |

使用禁止領域（`0xFEA0`–`0xFEFF`）の読み出しは3番目のケース。
「使用禁止」は**プログラマへの規約**であって**ハードウェアの禁止ではない**。
実機のCPUはここを読んでも止まらず、何も繋がっていないバスの値（`0xFF`）が返るだけ。
実際のゲームは、OAM走査の境界計算ミスなどでここを読むことがある。
→ **実機で動くROMがエミュレータでだけ落ちる**のが最悪の事態なので `0xFF` を返す。

## 付録C: コンパイラが守ってくれる範囲

```
守る:    型が合っているか / match に穴がないか / 所有権
守らない: 引き算の定数が正しいか / 仕様通りの値を返しているか
```

Echo RAM のバグ（`wram[49152]`）も、`panic!` の乱用も、**どちらもコンパイルは通る**。
配列長は実行時にしか分からず、`panic!` はそもそも文法的に正しいため。
rust-analyzer を入れても、捕まえてくれるのは**型と網羅性**まで。

→ だから**ユニットテストを書く**。

### C.1 ただし、テストの書き方しだいで一部はコンパイル時に引き上げられる

境界値テストが**リテラルの添字**を使っていると、配列長がコンパイル時の契約になる。
`hram` のサイズを `0x7F` → `0x7E` に減らす故障を入れたところ、
テストが赤くなる前に**ビルドが止まった**。

```
error: this operation will panic at runtime
   --> src/tests/bus_tests.rs:130:16
    |
130 |     assert_eq!(bus.hram[0x7E], 0x0C, "hram[0x7E] -> 0x0C");
    |                ^^^^^^^^^^^^^^ index out of bounds: the length is 126 but the index is 126
    |
    = note: `#[deny(unconditional_panic)]` on by default
```

添字も配列長もコンパイル時に確定しているため、rustc が「この行は必ず panic する」と判断する。
`unconditional_panic` は**既定でエラー扱い**のリント。

→ **「配列長は実行時にしか分からない」は、添字が変数のときの話。**
リテラルで書けるところはリテラルで書くと、検査が1段階前倒しになる。

## 付録D: 事故の記録 ― `cargo fmt` と「変更の破棄」

Busテストの途中で、**7時間分の未コミット作業を一時的に失いかけた**。手順を残す。

### 何が起きたか

1. `cargo fmt` を**プロジェクト全体**に実行してしまった（`normal.rs` だけで1815行の差分）
2. 元に戻そうとして VS Code の「**変更を破棄（Discard Changes）**」を押した
3. これは fmt を取り消す操作ではなく、**最後のコミット以降の変更を全部捨てる**操作だった
4. `Registers::new()` と、STOP / DAA / JP cc のバグ修正がすべて消えた

### どう復旧したか

**VS Code の Local History**（`~/.vscode-server/data/User/History/`）に、
fmt 直前かつバグ修正済みのバージョンが残っていた。

`cargo fmt` は**エディタの外から**ファイルを書き換えるので履歴に記録されない。
結果として「fmt直前の版」が最新履歴として残っていた、という巡り合わせに助けられた。
**ただし履歴には上限（1ファイル50件）があるので、当てにしてはいけない。**

### 再発防止

- **未コミットの変更があるときに `cargo fmt` をかけない。**
  かけるなら**コミット直後**。差分が全部フォーマット由来だと分かっていれば `git checkout -- .` で確実に戻せる
- 1ファイルだけ整形したいときは `rustfmt --edition 2024 <file>` を使う
  （`cargo fmt` は必ずプロジェクト全体に及ぶ。`--edition` が要るのは、単体で呼ぶと `Cargo.toml` を読まず既定が 2015 になるため）
- **節目ごとにコミットする。** untracked のファイル（`src/tests/` など）は git が存在すら知らないので特に危険

### 関連: インデントが1ファイルだけ5スペースになっていた件

VS Code の **`editor.detectIndentation`（既定で有効）** が、
ファイルの中身からインデント幅を推測してそのファイル限定で上書きする。
一度5スペースの行ができると「このファイルは5」と推測され、Tabが5スペースを入れ、
さらに5スペースの行が増える、という自己強化ループに入っていた。

`.vscode/settings.json` で止められる。

```json
{
    "editor.detectIndentation": false,
    "editor.tabSize": 4,
    "editor.insertSpaces": true
}
```
