# 命令テスト設計シート

`emulator/src/tests/normal_tests.rs`（今後の `cb_tests.rs` も同じ）にテストを1本書き始める前に、
**その命令が実機で何をしているか**と、**何を・どの値で・どういう順に検証するか**を確定させる。

## この Skill の位置づけ

- **規則の本体は `docs/TEST_RULES.md`。** 値表・命名・assert 順序・共通化の線引きはすべてあちらが正。
  この Skill は「それを毎回同じ順で適用し、同じ形で出す」ためだけのもの。
  両者が食い違ったら **`docs/TEST_RULES.md` に従い、食い違った箇所を報告する**（この Skill の更新漏れなので）。
- 上位の原則は `docs/RESUME_GUIDE.md` 4.4（検証すべき5項目）と 4.5.1（原則①〜⑧）。

## 絶対に守ること

`gb_emulator/CLAUDE.md` の禁止事項はこの Skill でも外れない。**手を動かして書くのは本人。**

- **そのまま貼れるテストコードを出さない。** `#[test] fn ...` の本体、完成した `assert_eq!` の行、
  Arrange のコード行、差分形式（`-` / `+`）のいずれも書かない
- 出してよいのは、**日本語の指示**と、API / 型名の**1〜2行の断片**
  （例:「HL は `set_hl()` で入れる。`get_hl()` は初期値 `0x0000` を返すだけ」）
- **値は決め打ちで出してよい。** `0x5A` `0xC100` などは規則から機械的に決まるもので、
  ここを毎回考えさせないことが規則の目的（`docs/TEST_RULES.md` 冒頭）
- assert のメッセージ欄は**下書き**。本人が読んで自分の言葉で書き直す前提で置く
  （原則⑤の検出力は「手で書くから矛盾に気づける」ところにある）。**そう毎回添えはしない**

## Step 0. 入力を解決する

**何を渡されても、まず「対象の match アーム1つ（または範囲）」と「テスト1本の主張」に落とす。**
opcode 決め打ちで呼ばれるとは限らない。

| 渡されたもの | 例 | やること |
|---|---|---|
| **opcode** | `0x2A` / `0xF1` | そのまま対象。`normal.rs` の該当アームへ |
| **ニーモニック** | `POP AF` / `LD A, (HL+)` | `docs/OPCODE SPECIFICATION.md` と `normal.rs` のコメントから opcode を引く |
| **テスト関数名** | `pop_af_masks_lower_nibble` | `grep -n 'fn <名前>' emulator/src/tests/normal_tests.rs`。**下の「テスト名から引く場合」を読む** |
| **グループ / 範囲** | 「LD r, r 全部」「CB の BIT 全部」 | 網羅ループとして扱う（末尾の差し替えテンプレ） |
| **曖昧な指定** | 「次に書くやつ」「ローテート系」 | 勝手に決めない。`#[ignore]` の残りから候補を3〜5件出して選んでもらう |
| **落ちているテスト名** | `cargo test` の出力から | まず原則⑥（疑う順番はテスト自身 → 実装）。設計シートは「既存を検算する」用途で使う |

解決した結果はシート1行目に書く。**2つ以上の候補が残ったら、そこで止めて確認する。**

### テスト名から引く場合（これが主経路）

`normal_tests.rs` には `#[ignore]` 付きの空スタブが計画として並んでいる。名前はすでに決まっている。

1. **名前が宣言している主張を読み取る。** `pop_af_masks_lower_nibble` なら
   「POP AF で F の下位4bitが 0 にマスクされること」。**これがそのテストの主目的**になる
2. **主張はスコープを絞る。** 「POP AF のテスト」ではなく「下位ニブルのマスクのテスト」なので、
   assert 表の1番（命令の主目的）はマスクの検証にする。
   命令全体の網羅ではないぶん、**同じ opcode の他の関心が別テストに分かれていないか確認する**
   （原則④。分かれていなければ「追加で出すもの」として持っておき、聞かれたら出す）
3. **書きかけの本体は根拠として読むが、粗探しの報告はしない。** 前の命令のブロックをコピーした
   残骸（古い `opcode`、使わない変数、`#[ignore]` の付け外し）が残っているのは日常茶飯事で、
   **シートの「値」の行に正しいものを並べれば、本人が並べ替えるときに自然に直る。**
   「ここが残骸です」とは書かない
4. 名前が実装と合わなくなっていたら（仕様の理解が変わった等）、シートには出さず
   「追加で出すもの」に回す

## 手順

### Step 1. 根拠を読む

1. `emulator/src/cpu/instructions/normal.rs`（CB なら `cb.rs`）から対象の match アームを読む。
   **実装が正解表**なので、Step 2 の問いは機械的に埋まる
2. 仕様側を `docs/OPCODE SPECIFICATION.md`（CB は `docs/CB_SPECIFICATION.md`）で確認する。
   フラグ欄の `*` は「演算で計算される」とは限らない ― **何によって決まるのか**まで見る
   （`POP AF` の `* * * *` は「スタックの値で丸ごと置き換わる」の意味）
3. ハードウェア側の根拠を `docs/SPECIFICATION.md` で確認する（F の下位4bit、メモリマップ等）
4. **実装と仕様がずれていたら、そこで止めて報告する。** ずれたままテストを設計すると
   「実装に合わせたテスト」ができあがり、バグを固定してしまう
5. 同じ opcode を扱う既存テストがないか確認する
   （`grep -n '0xNN' emulator/src/tests/normal_tests.rs`。`#[ignore]` の空スタブも含めて見る）

### Step 2. 5つの問い（+演算命令なら6つ目）に答える

`docs/TEST_RULES.md` 1章の表に従う。答えの根拠として **`normal.rs` の行番号**を必ず添える。

- 番地の調達元は **PC（即値）/ レジスタペア / SP / 命令に埋まった定数** の4種しかない
- PC を特別扱いしない。**即値を使う命令だけ**が PC を読む

### Step 3. 値を割り当てる

`docs/TEST_RULES.md` 2章の固定表から選ぶ。その場で考えない。
複数ブロックを1本に入れるなら、ブロックごとに `addr` を `+0x0100` する（7章）。

### Step 4. 「仕様」の段落を書く ― ここがシートの本体

実装の match アームは**何をするか**しか教えない。シートの価値は、その手前にある
**なぜそうなっているか**と、**このテストで何を言い切りたいのか**を短く言語化するところにある。
2〜4行で、次の3つを埋める。

1. **実機で何が起きているか。** ハードウェアの事実を書く
   （例: F は下位4bitの回路が存在しないので、どこから何を書いても 0 に落ちる）
2. **同種の他命令とどう違うか。** 差分が分かると、その命令を覚えなくてよくなる
   （例: `POP BC/DE/HL` は素直に2バイト戻すだけだが、`POP AF` だけ F 側にマスクが挟まる）
3. **このテストが証明すること / しないこと。** 名前でスコープが絞られている場合は特に重要
   （例: このテストはマスクを言い切るが、`PUSH AF` との往復が壊れていないことは言わない）

**`docs/TEST_RULES.md` の再掲はしない。** ここに書くのは規則の説明ではなく、ハードウェアと
その命令の説明。値の選び方・命名・assert 順序の理由づけは規則側の仕事なので書かない。

### Step 5. シートを出力する

下の出力フォーマットに**そのまま**従う。**埋まらない行は行ごと省く**（「該当なし」とも書かない）。
Step 1〜4 で読んだ経緯（どのファイルを grep した等）は出力しない。
**シートの前にも後にも文を付けない。** 「では設計しましょう」「以上です」も、
締めの注意書き（下書きである旨・赤を見る話・コミットの促し）も、シートには付けない。

聞かれたら補足する事項（`cargo test <名前の一部>` / `-- --nocapture` /
ミューテーションはコミット済みの状態でだけ試して必ず戻す）は、**聞かれるまで出さない**。

## ファイル参照はすべてリンクにする

シート内で行番号に触れるときは、**クリックで飛べる markdown リンク**にする。
パスは**ワークスペースルート（`RustProjects/`）からの相対パス**。`gb_emulator/` から始まる。

| 書くもの | 形 |
|---|---|
| 実装のアーム | `[normal.rs:1384-1389](gb_emulator/emulator/src/cpu/instructions/normal.rs#L1384-L1389)` |
| テストの位置 | `[normal_tests.rs:354](gb_emulator/emulator/src/tests/normal_tests.rs#L354)` |
| 仕様の行 | `[OPCODE SPECIFICATION.md:178](gb_emulator/docs/OPCODE%20SPECIFICATION.md#L178)` |

- 範囲は `#L<開始>-L<終了>`、単一行は `#L<行>`
- **パスに空白があれば `%20`**（`OPCODE SPECIFICATION.md` が該当）
- 「壊す」行で `normal.rs:1385` のように行を指すときも、同じ形でリンクにする
- バッククォートで囲まない（リンクが効かなくなる）

## 出力フォーマット（固定・1画面）

**画面分割の片側で読むので、全体で30行以内に収める。** そのための規則:

- **表は assert の1つだけ。** 他は1行に詰める
- **正常な項目は書かない。** 「一致」「該当なし」「なし」だけの行は**行ごと省く**
- **スタブの状態を報告しない。** 残骸の変数・古い `opcode`・`#[ignore]` の有無は書かない
  （正しいものを「値」の行に並べることで足りる）
- `⚠` を出すのは**作業が止まる2件だけ** ― 実装と仕様の食い違い / 対象が1つに定まらないとき
- 値の選び方に理由を添えない（規則で決まっているものを再説明しない）。
  ただし**踏むと壊れる前提**（`new_cpu()` が SP を入れない 等）は「罠」に書く
- 深掘りは**聞かれたら**出す（末尾の「追加で出すもの」）

````markdown
`<テスト名>` = 0xNN `MNEMONIC` ― <この名前が宣言している主張>
実装: [normal.rs:NNN-NNN](リンク) / テスト [normal_tests.rs:NNN](リンク) / 仕様 [OPCODE SPECIFICATION.md:NNN](リンク)
⚠ <実装と仕様の食い違い / 対象が定まらないときだけ>

仕様: <実機で何が起きているか。ハードウェアの事実>
     <同種の他命令との違い>
     <このテストが証明すること / しないこと>

読: <番地と調達元>  書: <番地と調達元>  PC: <±N>  変: <レジスタ>  cycle: <N>  F: <Z:… N:… H:… C:…>

値: opcode=0xNN  <name>=<v>  <name>=<v>  <name>=<v>

| # | 実際 | 期待 | メッセージ / 行末コメント |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |
| 4 | `cpu.registers.F` | `F_BEFORE` | `"F 不変"` |
| 5 | `assert_pc_and_cycle` | `PC_BEFORE`, `N` | |

罠: <この命令固有のもの・踏むと壊れる前提があるときだけ1行>
赤: <どの assert をどうずらすと落ちるか。1行>
壊: <実装のどこ（リンク）を壊すと何番だけが落ちるか。1行>
````

- 「値」の行の先頭は必ず `opcode=0xNN`。ここが本体の `let opcode = ...;` の正解になる
- assert の並びは `docs/TEST_RULES.md` 6章の固定順（主目的 → 副作用 → 不変 → F → PC → cycle）。
  **1番には必ず「名前が宣言している主張」を置く**
- PC と cycle は `assert_pc_and_cycle(&cpu, opcode, <期待PC>, cycle, <期待cycle>)` の1行に畳む。
  2行に分けない（この関数が `opcode` と `#[track_caller]` を持っている）
- 命令が F を置き換える場合（`POP AF` など）、4番の「F 不変」は**成立しないので行ごと省く**。
  その旨は「仕様」の段落で説明済みにしておく

### メッセージ欄の書き方 ― 既存テストの形に揃える

**既存の `normal_tests.rs` に出ている形だけを使う。** 新しい言い回しを発明しない。

| 種類 | 形 | 例 |
|---|---|---|
| 主目的・副作用 | **`<入力式> -> <転送先>`** の矢印式。散文にしない | `"A + B -> A"` `"(HL) -> A"` `"HL -> HL+1"` `"B + 1 -> B"` `"n -> B"` |
| F 全体（`cpu.registers.F`） | **`"ZNHC -> 0010"`** の4桁ビット。不変なら `"F 不変"` | `"ZNHC -> 0001"` |
| F の1bit（`F & 0x80` など） | **`"<bit> -> <値>"`** | `"Z -> 0"` `"H -> 0"` |
| 触っていないもの | **`"<名前> 不変"`** | `"B 不変"` `"(HL+1) 不変"` |

- **メッセージが名乗る範囲を、`assert_eq!` の第1引数が見ている範囲に合わせる。**
  `cpu.registers.F` を丸ごと比較する行は4bit分を主張しているので、`"C -> 1"` のように
  1bitだけ名乗らせない（Z の消し忘れで落ちたときにメッセージが別のビットを指してしまう）。
  1bit形を使うのは**マスクして取り出している行だけ**

- **単一 opcode のテストでは `"0x{:02X}: ..."` の接頭辞を付けない。** `assert_pc_and_cycle` が
  opcode を持っているので、どの命令で落ちたかは必ず出る。
  接頭辞を付けるのは **網羅ループ** と **1本に複数 opcode のブロックを入れたとき**だけ
  （`docs/TEST_RULES.md` 5章③ の「要る」はこの2つを指す）
- **理由・補足・ビット列・計算は、メッセージではなく行末 `//` コメントに回す。**
  メッセージ欄に `(旧bit7 -> C)` のような括弧書きを足さない。
  シートではメッセージの右に ` // ...` を続けて書いて区別する
- **メッセージに「他のテストと区別できる文言」を求めない。**
  命令を区別するのはテスト関数名（失敗表示に必ず出る）で、メッセージの役目は
  **1本のテストの中で落ちた assert を言い分けること**だけ。
  `"A << 1"` が RLCA と RLA の2本に出るのは正しい ― `"ZNHC -> 0000"` や `"F 不変"` も
  同じように共有されている（`docs/TEST_RULES.md` 5章②）。
  **シートのレビューでも「同じメッセージが別テストと重複している」を指摘しない**

```
期待どおり:  "A << 1"          // 0b1010_0101 -> 0b0100_1011 (Aのみで環状)
             "ZNHC -> 0001"    // 入力問わずCに触れない(C=1)
             "A + B -> A"      // 19+28=47
やりすぎ:    "0x07: A<<1 | bit7 -> A (旧bit7 -> C)"
```

### 追加で出すもの（聞かれたときだけ）

シートには載せない。「分割は?」「他にどう壊せる?」などと聞かれてから出す。

- 分割の判断（原則④）と、残りの関心をどのテストが引き受けるか
- ミューテーション案の追加（理想は1故障で1〜2本。5本落ちるならまとめすぎ、0本なら穴）
- 関数名の再検討案
- Arrange の詳細（**変わるレジスタへの目印**を入れ忘れていそうなときは「罠」で出す）

## 網羅ループの場合

`*_all_registers` / `*_all_pairs` / `*_all_sources` を渡されたらこちら。
参照実装は `ld_r_r_all_opcodes`。上のフォーマットの「読〜値」の2ブロックを次に差し替える
（「仕様」の段落は残す ― 網羅ループこそ「何を一括で言い切るのか」が要る）。

````markdown
範囲: 0xNN..=0xNN  基準表: `REG_INIT`  パラメータ: ddd=(op>>3)&7 sss=op&7
skip: <continue する条件>  count: <期待件数>

要点: Arrange の内側ループで毎回全レジスタを init に戻す / ddd 以外も全部検証 / 最後に count
````

assert のメッセージには `opcode` と `index` の両方を埋める（`"0x{:02X}:"` の接頭辞が要るのは
網羅ループと複数 opcode のブロックだけ ― 上の「メッセージ欄の書き方」参照）。添字は `usize`。
